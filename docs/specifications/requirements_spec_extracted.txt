Requirement Specification
Multimodal Emotion Recognition Pipeline
(Core model/pipeline scope — for the mental-health tracking app's primary detection feature)

0. Purpose and Scope of This Document
This document defines the requirements for the multimodal emotion recognition pipeline itself — not the full mental-health app around it. The app context (digital-footprint tracking, in-app/out-of-app activity monitoring, dashboards) is treated only as the reason this pipeline exists; it is out of scope here. The goal is to reach a 'recognition of need' precise enough that a later architectural decision — a modality-specific classifier pipeline with a fusion layer, versus a fine-tuned multimodal LLM — can be made by checking which approach actually satisfies these requirements, rather than picking an approach first and rationalizing it afterward.
The primary use case driving every requirement below: the user opens the app, starts a session (camera optionally on, microphone on, or text-only chat), and rambles freely about their day — either to themselves, to a journaling prompt, or to a conversational agent — for anywhere from under a minute to many minutes. The pipeline's job is to continuously extract emotional signal from this session at a useful granularity, cope gracefully with real recording conditions and interruptions, and produce output that is usable by the mental-health tracking layer above it.
1. Input Modalities and Session Modes
The pipeline must support three distinct session modes, since the app explicitly does not force camera use:

1.1 Requirement: mode must be a first-class input to the model, not an afterthought
R1.1 — The pipeline MUST accept and correctly process all three modes above without requiring code changes per mode — i.e., missing modalities are a normal, expected input state, not an error state.
R1.2 — The pipeline MUST report, per output, which modalities were actually used to produce that output (so the app layer and the user can see when a reading is voice+text-only vs. fully multimodal).
R1.3 — Typed-text-only input (no speech at all) MUST be supported as its own valid path — this is a text-emotion-classification problem, not a degraded version of the audio pipeline, and should not force fabricated 'silence' audio/video features.
1.2 Recording condition parameters (environment) — explicit factors to specify, test, and report against
These are the real-world variables the literature review flagged as the field's central open problem (in-the-wild robustness). For a spec to be complete, each must have a stated minimum bar and a stated 'known degraded' zone, not be left implicit.
2. Temporal Granularity: The Utterance as the Core Unit
Per your decision, the model's fundamental unit of output is the utterance/sentence, bounded by natural pauses — not a fixed time window and not a whole-session summary. This has direct architectural consequences that must be specified precisely, because 'utterance' is not a free primitive — it must be detected from raw audio/video first.
2.1 Utterance boundary detection
R2.1 — The pipeline MUST include a voice-activity-detection (VAD) + pause-length-based segmentation stage that converts a continuous audio stream into discrete utterance boundaries, since no reviewed model performs this end-to-end (literature review, Section 8).
R2.2 — A configurable pause-length threshold MUST separate 'end of utterance' from 'mid-thought pause' — e.g., a short pause (under ~1.5–2s, exact value to be tuned empirically) is treated as continuation of the same utterance; a longer pause is treated as an utterance boundary.
R2.3 — Utterance boundaries MUST NOT depend on ASR transcript punctuation alone (punctuation from streaming ASR is unreliable and lagged) — timing-based (pause) segmentation is the primary signal, with transcript sentence structure as a secondary/refining signal where available.
R2.4 — The system MUST support utterances that are sub-sentence fragments (per your own description — 'may not even be a full sentence') — the unit is defined by pause-bounded speech, not by grammatical completeness.
2.2 The interruption / episode case
Per your decision: when a user pauses mid-thought (distraction, interruption, collecting themselves) and then resumes, the two speech segments should be linked as one 'episode' with a noted gap, rather than treated as fully independent utterances or silently merged.
R2.5 — The system MUST distinguish at least two categories of pause: (a) a completion pause (end of a thought, next utterance is topically new) and (b) a resumption pause (same thought continues after a gap). This likely requires a combination of pause duration AND topical/semantic continuity of the text before and after the gap — a heuristic-plus-model problem, not pure silence-duration thresholding.
R2.6 — When a resumption pause is detected, the system MUST represent the two speech segments as one linked 'episode' in its output structure (e.g., a parent episode ID with child utterance segments), preserving the gap duration and, where derivable, a reason/annotation for the gap (e.g., 'long pause, no visible cause' vs. 'user was looking away/distracted, inferred from gaze' — the latter requires gaze/attention estimation from video, which is a stretch goal, not an MVP requirement).
R2.7 — During the gap itself (the silent period inside an episode), the facial-only signal MUST still be tracked and attached to the episode as its own labeled sub-segment (see Section 3), not discarded.
2.3 Aggregation above the utterance level
R2.8 — In addition to per-utterance output, the pipeline MUST support session-level aggregation (e.g., dominant emotion, emotional volatility/variance across utterances, trend over the session) since the app layer will need this for daily/weekly tracking — this is a downstream aggregation of utterance-level outputs, not a separately trained 'whole-session' classifier.
3. Non-Speech (Silent) Periods
Per your decision: while the user is not speaking, facial expression should still be tracked as its own independent signal, distinct from in-speech facial expression.
R3.1 — The pipeline MUST produce a facial-only emotion signal for silent periods (both between utterances and during a mid-episode gap), using the same facial model as the in-speech facial branch, but reported as a distinct segment type ('silent-facial') rather than merged into any utterance's fused label.
R3.2 — The system SHOULD support comparing a user's silent/'resting' facial affect against their in-speech facial affect within the same session (e.g., did their expression change the moment they started talking about a specific topic) — this was identified in the literature review as a genuinely novel angle with no direct existing model, so it should be treated as an explicit, named capability rather than an implicit byproduct.
R3.3 — Minimum silence duration to bother running facial inference on MUST be defined (e.g., don't bother classifying a 200ms micro-pause between words) — likely on the order of 1–2 seconds, to be tuned.
R3.4 — If the camera is off (voice-only or text-only mode), silent-period facial tracking is simply unavailable — this MUST degrade gracefully (empty/null segment, not an error) per Section 5.
4. Per-Modality and Fused Output Requirements
Per your answer: because the classifier-vs-LLM decision changes what's possible here, this section specifies the output contract in a way that both architectures can satisfy, then explicitly separates the parts that only make sense for one path.
4.1 Baseline output contract (required regardless of architecture)
R4.1 — For every utterance (or silent segment), the system MUST output a per-modality emotion signal for each modality that was available: facial signal, voice/tone signal, and text/lexical-content signal — reported separately, not only as a black-box fused number.
R4.2 — The system MUST additionally output one fused emotion label/score representing the combined judgment across available modalities for that segment.
R4.3 — Each of the three per-modality outputs AND the fused output MUST carry its own confidence score, not a single shared confidence — a segment can have high facial confidence and low voice confidence simultaneously (e.g., loud background noise but a clear, well-lit face).
R4.4 — The system MUST expose which modalities contributed to the fused output and their approximate relative weight/contribution, to satisfy the audit requirement identified in the literature review (avoiding silent 'modality laziness' where fusion secretly ignores a modality).
4.2 Incongruence / conflict handling
This is the case you flagged directly — calm words, shaky voice tone, tense face — i.e., the user may be masking or unaware of their own emotional state, which is precisely the kind of signal a mental-health app most wants to catch.
R4.5 — The system MUST be able to detect when per-modality signals diverge beyond a defined threshold (e.g., text sentiment is neutral/positive while voice-tone and facial signal both indicate distress) and MUST surface this as an explicit 'incongruence' flag on the segment/episode, independent of which architecture is chosen.
R4.6 (classifier-path specific) — If a modality-specific classifier + fusion-layer architecture is chosen, incongruence detection is computed as a rule/statistical check across the three separate per-modality output vectors (e.g., cosine distance between modality-specific emotion-probability distributions, or a simple valence-sign mismatch check) — this does NOT require a specially trained 'incongruence' model, it is a downstream comparison of already-required per-modality outputs (R4.1).
R4.7 (LLM-path specific) — If a fine-tuned multimodal LLM approach is chosen, the model MAY additionally generate a natural-language explanation of the detected incongruence (e.g., 'the user's words suggest calm, but vocal tremor and a tense expression suggest underlying anxiety') — this reasoning-output capability is unique to the LLM path and should be scoped as an LLM-path-only requirement, not assumed achievable from a classifier pipeline without substantial additional engineering (see literature review Section 6, Emotion-LLaMA).
R4.8 — Given the combinatorial explosion you flagged (3 modalities × N emotion classes each × fused label × incongruence flag), the specification MUST fix a small, closed emotion label set (see Section 6) before implementation — an open-ended or very large label space will make both the classifier and LLM paths intractable to validate.
5. Missing-Modality Handling and Graceful Degradation
Per your decision: the system should never block the user for not using the camera. Camera-off, voice-only, and text-only are all normal, permanent states for a given session (not transient failures), while a mid-session camera obstruction or a mid-session silence is a transient state within an otherwise multimodal session. The spec must treat these as two distinct cases.
5.1 Case A — modality unavailable for the whole session (user's deliberate choice)
R5.1 — When video is unavailable for an entire session, the pipeline MUST run on voice+text only, and the facial-modality field in every output MUST be explicitly marked 'not available' (not zero, not a guessed neutral value) — this distinction matters for the app layer's own confidence handling and for later analytics (don't let 'no data' silently become 'neutral face' in the aggregated mood history).
R5.2 — When only text is available (typed chat, no audio/video at all), the pipeline MUST run pure text-emotion classification and MUST NOT attempt to fabricate voice or facial features — this is architecturally the simplest path and should reuse a standard text-emotion/sentiment classifier rather than being treated as a degraded multimodal case.
5.2 Case B — modality drops mid-session (transient: camera blocked, user turns camera off partway, connection drop, user goes silent)
R5.3 — The pipeline MUST detect transient modality loss per segment (e.g., no face detected in frame for N consecutive seconds; audio level below noise floor for N seconds) and gracefully fall back to the remaining modalities for exactly those segments, resuming full multimodal processing automatically once the modality returns — no session restart, no pausing of output, per your explicit answer.
R5.4 — Confidence scores (R4.3) MUST be lowered specifically for the affected modality/segment when a transient drop is detected, distinct from a full-session absence (R5.1) — the two cases should be visually/structurally distinguishable in the output, since one is 'user chose not to' and the other is 'something interrupted the expected signal.'
R5.5 — The system SHOULD log (internally, for later model improvement — not necessarily surfaced to the end user) how often and under what conditions transient drops occur, since this is exactly the kind of real-world degradation the literature review flagged as under-tested (Section 8, ABAW in-the-wild gap).
6. Emotion Taxonomy and the Two-Stage Labeling Requirement
Per your decision: the target output should use mental-health-oriented labels (e.g., stressed, anxious, low-mood, calm) rather than generic Ekman-style categories. This decision has a direct data-availability consequence that must be written into the spec explicitly, because it changes the required training pipeline regardless of which architecture (classifier or LLM) is eventually chosen.
6.1 The core problem: mental-health labels have very little direct public training data
Large public datasets (FER2013, AffectNet, RAVDESS, CREMA-D, IEMOCAP, MELD) are labeled with generic/basic emotions (happy, sad, angry, fear, disgust, surprise, neutral) or with sentiment polarity — none are labeled natively with 'anxious' / 'stressed' / 'low-mood' at the utterance level. The closest existing resource, DAIC-WOZ/E-DAIC, gives a single depression-severity score per full session/participant, not per-utterance mood labels.
R6.1 — The system MUST define its target label set as a fixed, closed taxonomy before any modeling work begins (recommended starting point below) — this is a project decision, not something to leave open-ended.
R6.2 — Because no large public dataset directly provides these labels at utterance granularity, the pipeline MUST be built as a two-stage labeling pipeline: Stage 1 — pretrain/leverage models on generic emotion + dimensional (valence/arousal) data (the well-supported public datasets); Stage 2 — define and apply an explicit mapping/fine-tuning layer from generic-emotion-and-valence-arousal space into the mental-health-oriented label set.
R6.3 — The Stage-2 mapping (R6.2) MUST be explicitly documented and justified (e.g., 'high arousal + negative valence + specific lexical markers → anxious' as a rule-based starting point, or a small supervised fine-tuning step on a purpose-collected/annotated dataset) rather than asserted as automatic — this mapping is itself a research contribution worth writing up, not an implementation detail to skip past.
R6.4 — A dimensional (valence-arousal) score SHOULD be retained and exposed alongside the mental-health categorical label, even though the categorical label is the primary output — dimensional scores are continuous, easier to track as a trend over time (useful for the app's tracking function), and are better-supported by existing datasets, giving a robustness fallback if the categorical mental-health labels prove too noisy in practice.
6.2 Suggested starting label set (to be validated, not treated as final)

R6.5 — 'Neutral / flat' MUST double as the explicit fallback label when confidence across all available modalities is too low to commit to a more specific label — the system should prefer an honest 'insufficient signal' outcome over a falsely confident specific label, especially given the mental-health stakes of over/under-flagging distress.
7. Requirements Mapped to the Classifier-vs-LLM Decision
This is the section meant to directly answer your framing question: which requirements are satisfiable by either approach, and which ones effectively force a choice.

Reading across this table: the classifier-plus-fusion approach satisfies more of the requirements more cheaply and is the lower-risk MVP path, particularly given the real-time and on-device privacy goals already stated in your original proposal. The LLM path's unique advantage — genuine natural-language reasoning about incongruence — is a real capability gap versus the classifier path, but it is also the least validated in the literature for this exact use case (no reviewed paper does real-time, streaming, incongruence-aware reasoning). A reasonable phased recommendation: build the classifier+fusion pipeline first to satisfy the bulk of these requirements and establish a working baseline and evaluation protocol, then treat LLM-based reasoning as an explicit Phase 2 upgrade layered on top for the explanation/'why' capability — which mirrors your own proposal's existing 'Future Extensions' framing (Section 9 of the original proposal) rather than contradicting it.
8. Non-Functional Requirements
8.1 Latency and streaming
R8.1 — The system MUST NOT require the entire session to complete before producing any output — utterance-level output must be emitted incrementally as each utterance completes (streaming/near-real-time), since the app's value (daily check-ins) benefits from at least near-live feedback and this also bounds memory use for long sessions (R1.8).
R8.2 — A target end-to-end latency per utterance (from end-of-utterance detection to emitted label) SHOULD be defined once an architecture is chosen — literature precedent (Section 8 of the lit review) suggests sub-second is achievable for a lightweight classifier pipeline; this is unlikely to be true unmodified for an LLM-scale path.
8.2 Privacy and data handling
R8.3 — Given the sensitivity of mental-health-labeled emotional data, raw video/audio SHOULD be processed and discardable immediately after feature extraction wherever feasible, retaining only derived features/labels rather than raw recordings by default, unless the user explicitly opts into raw-recording retention (e.g., to re-watch a journal entry).
R8.4 — Consistent with the original proposal's 'privacy-preserving AI' objective, on-device inference SHOULD be the preferred target for at least the facial and voice branches, with server-side processing (if used at all) clearly disclosed to the user.
8.3 Evaluation and validation
R8.5 — Evaluation MUST be run under conditions matching Section 1.2 (varied lighting, noise, device, session length) — not only under clean, curated benchmark conditions — before any accuracy claim is treated as representative of real usage.
R8.6 — Given the mental-health stakes, false-negative behavior (missing real distress) and false-positive behavior (flagging distress that isn't there) SHOULD be evaluated and reported separately, not collapsed into a single accuracy number — the acceptable error profile is not symmetric for this application.
R8.7 — The system's own scope disclaimer MUST state clearly (to users and in documentation) that it is a self-reflection/tracking aid, not a diagnostic or clinical tool — consistent with how every mental-health-adjacent paper in the literature review frames itself (Section 7 of the lit review).
9. Open Questions Still Needing a Decision
These are the points this conversation surfaced but did not fully resolve — worth deciding explicitly before implementation begins, since each one materially affects scope:
Exact pause-length thresholds for (a) utterance boundary vs. (b) episode-continuation gap — these need empirical tuning against real or pilot recordings, not a value chosen from first principles.
How much effort to invest in gaze/attention estimation for inferring a 'reason' for an interruption gap (R2.6) — this is a nice-to-have that adds real computer-vision complexity; worth explicitly deciding it's out of scope for MVP if time is limited.
Whether primary-speaker face/voice selection (R1.9) needs to handle multiple people robustly for MVP, or whether it's acceptable to assume a single-user, single-face session at launch.
The incongruence-detection threshold (R4.5) — how much disagreement between modalities counts as meaningful incongruence versus normal noise — will need empirical calibration, likely against a small hand-labeled validation set you create yourselves, since no public dataset labels this directly.
Whether the Stage-2 label mapping (R6.2–R6.3) is initially rule-based (fast, transparent, easier to justify in a system-design report) or learned via a small fine-tuning dataset you collect (more accurate, but adds a data-collection task to the project timeline) — this is likely the single highest-leverage scoping decision left.
Target minimum session length/data volume for a believable pilot evaluation — since public datasets don't match your real use case well (Section 8 of the lit review), some amount of self-collected or volunteer-collected pilot data is probably unavoidable, and its scale should be decided now rather than discovered as a blocker later.
